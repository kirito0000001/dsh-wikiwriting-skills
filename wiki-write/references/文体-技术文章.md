> **每条规范自带四字段**（接 `03_接口_v0.5.md` §9）：每条规则行末带 `〔源键｜依据类型｜版本与实施日期｜适用文体〕`；源键表见 §5.0。

> ⚠️ **本骨架的来源密度不均**：结构依据几乎全部来自一家公司**真在用的**工程博客写作规范（Sentry，Apache-2.0）；另一份来源（Grafana）只给了**出版流程**，**没有给任何结构规范**。凡"某来源要求某段而另一来源不要求"的地方，本文一律**只记不选边**；凡是我们自己推出来的，逐条标「本轮推导」。

## 0. 适用与不适用

**用这个骨架**（条件）：产物是**给别人看的、署名的技术文章**——工程博客、技术号、内部分享长文。读者是同行工程师，他要在**滚动信息流**里决定要不要点开，点开后要在**前两句**内决定要不要读下去。

**不用这个骨架**（要求 → 换哪个骨架）：

| 情形 | 为什么不用 | 换成 |
| --- | --- | --- |
| 产物只有一个版本号级别的变化要说 | 变更日志才是它该待的地方；文章必须提供比变更日志更多的东西 | `CHANGELOG` |
| 产物是让读者"开始用起来"的入门路径 | 那是 README / 教程的活；技术文章的读者预期是"学到点什么"或"看懂一个决策" | `文体-README.md` 或教程文档 |
| 产物是完整 API 参考 | 参考材料要"准确完整、无解释无观点"，与技术文章的目标正相反 | 参考文档 |
| 产物不署名、以团队/公司名义发布 | 本骨架有一条硬规则：**没有真实人名署名的文章不得发布** | 公告/新闻稿体裁 |
| 产物是纯营销文案（预告、促销） | 本骨架的非商量条款与大半规则都会与之冲突 | 营销文案，另定骨架 |
| 内部设计决策、只给同事看 | 本骨架的"开头必须先给问题或结论""必须交代取舍"等仍适用，但 SEO 型规则整节可不适用 | 仍可用，按 `WRT-TA-S06` 的例外停用 SEO 组 |

**一条必须先确认的事**：**这篇文章属于哪一型**（见 §1.1）。分型决定署名归属、必备段、要不要 SEO 组——不先定分型就开始写，是后面所有返工的源头（→ `WRT-TA-S11`）。

### 0.1 与采集侧的接口（`03_接口_v0.5.md` §7 / §9）

- **§7 留痕** → 校对版正文保留 `〔A-nn〕` 角标（**全角六角括号**，紧贴前字），发布版由 `tools/publish.mjs` 机械隐藏；两版同源，只差显示层。**别为了发布版干净就在采集时省掉 ID。**
- **§9 消费** → 每个性能数字的**措辞强度**必须匹配账本 `状态`。技术文章最典型的越界是：把 `自测` 的结果写成不带测量条件的普适结论，或把 `二手线索` 写成确定事实。
- ⚠️ 技术文章比 README **多一道最贵的门槛**：`§4.5` 的"到位"标准要求性能数字达到 `5.7｜RTX4090/32G｜场景X（资产A）｜基线120→148fps｜stat unit ×3 取中位｜原始数据 chart.csv` 这种颗粒度，判据是**别人能不能复现这次测量**。来源只说"要带数字"，**没说要带这些条件**——这一层是 `03_接口` 补的，落实到 `WRT-TA-R05`。

## 1. 结构骨架

### 1.1 先分型：五型与各自的署名归属

| 型 | 目标 | 署名归属 | 必备的额外段 |
| --- | --- | --- | --- |
| **工程深潜** | 讲清一个技术系统或决策，让别的工程师学到东西 | **真正做它的工程师本人，没有例外** | "试过但没用的" + "已知局限"（§1.3） |
| **产品发布** | 说清发布了什么、为什么重要、怎么用 | PM / 工程师 / DevEx；**营销未参与构建时不得署营销** | "怎么用起来"段 |
| **复盘（事故/失败）** | 透明地做失败分析，含时间线与修复 | 工程负责人 | 时间线 + 修复 + 遗留风险 |
| **数据/研究** | 用独有数据位置给出原创洞察 | 数据团队 / 工程 / 研究 | 数据来源与方法 |
| **教程/指南** | 帮读者完成一件具体的事 | DevEx / 工程师 / 社区贡献者 | 可复制粘贴的步骤 |

> 分型的判据不是"内容长短"，而是**读者拿它做什么**：深潜给"理解"，发布给"判断要不要用"，复盘给"信任与教训"，数据给"别人拿不到的事实"，教程给"省下来的时间"。

### 1.2 通用分节清单（顺序与理由）

| # | 段 | 写什么 | 多长 | 为什么在这个位置 |
| --- | --- | --- | --- | --- |
| 1 | **标题** | 一个具体主张 / 一个故事 / 一个明确回报 | 1 行 | 标题是全篇**杠杆最高的一句**：它要在一个正在滚动信息流的开发者面前把滚动停下来 |
| 2 | **署名** | 真实人名（+ 分型对应的归属） | 1 行 | 读者判断可信度的第一依据；"团队成员"式署名等于放弃这个依据 |
| 3 | **开头 2–3 句** | **只说两件事之一**：问题是什么，或结论是什么 | 2–3 句 | 读者在这个窗口内决定去留；背景/公司史/预告会把这个窗口浪费掉 |
| 4 | **这解决什么问题** | 读者能对上号的痛点 | **最多 1–2 段** | 先让读者确认"这跟我有关"，再给技术 |
| 5 | **它到底怎么工作** | 底层机制、数据结构、协议、算法——**不是"点哪个按钮"** | **全篇主体**，最厚 | 这是文章的**存在理由**；也是"我会分享这篇吗"的主要来源 |
| 6 | **取舍与备选方案** | 没选什么、为什么没选、代价在哪 | 2–4 段 | 来源明写这一节是"好"与"极好"的分界 |
| 7 | **试过但没用的**（深潜型必写） | 走过的弯路、被否掉的方案 | 1–3 段 | 建立信任：读者知道你没藏东西 |
| 8 | **已知局限**（深潜型必写） | 什么情况下会坏、什么还没做完、beta 就说 beta | 1–2 段 | 智识诚实；也是读者最容易验证的部分 |
| 9 | **怎么用 / 试 / 落地** | 具体的下一步，不是"联系我们" | 1 段 + 代码块 | 把"读完了"变成"能动手" |
| 10 | **定义段**（SEO 型必备） | 目标词条的"What is X?"式定义 | 1 节 | 信息型查询下排名靠前的页面几乎都有这一节 |
| 11 | **FAQ**（SEO 型必备） | 3–4 个长尾问题 | 文末 1 节 | 抢精选摘要与"大家还在问" |
| 12 | **结尾** | 文档 / 源码 / 试用 / 反馈的**具体链接** | 1 段 | 回到开头那个故事，或给一件立刻能做的事 |

**顺序理由（一句话）**：整篇按**读者真正在想的问题**排，不按你的内部叙事排。读者的问题序列是"这跟我有关吗"→"它怎么做到的"→"还有没有别的做法"→"哪里会翻车"→"我现在能做什么"。§1.3 的两个段是深潜型对这个序列的补强。

### 1.3 SEO 型文章的排布调整（**动向相反，必须显式二选一**）

目标是竞争性搜索词时，上表有两处**要被覆盖**：

- **第 4–5 段的前后比例**：前半篇（约 50–60%）写**工具无关**的教育性内容（定义、概念、指标、最佳实践），产品作为**实现示例**放到后半篇。理由是搜索引擎对信息型查询把指南排在产品页前面。
- **第 10–11 段**（定义段 + FAQ）由"可选"升为"必备"。

⚠️ 这处覆盖与第 3 段的硬规则**直接紧张**：SEO 排布要求的"工具无关教育内容"在形态上就是背景铺垫，而第 3 段禁止以背景开场。**两边都保留，按目标分叉**：
- 目标是**搜索流量** → 用 §1.3 排布，但第 3 段的开头仍须**以一个问题或一个结论起句**，教育内容作为该问题的展开，而不是"先说行业背景"。
- 目标是**信息流分享 / 深潜 / 复盘 / 数据** → 严格用 §1.2，不加定义段与 FAQ。

## 3. 正反例

出处标注规则：`〔源〕` = 来自某来源（**意译/译写，非逐字**）；`〔自造〕` = 本轮据某条规则构造，**非源文**。

### 3.1 开头（最重要的一对）

| | 内容 | 出处 |
| --- | --- | --- |
| ❌ | "在 X 公司，我们一直在寻找改进开发者体验的方法。今天我们很激动地宣布……" | 〔源〕被来源直接列为反面示例的开场形态 |
| ✅ | "上线前两周，我们把整个指标产品砍了。下面说清为什么时序列预聚合在调试场景下会崩，以及我们怎么从零重建。" | 〔源〕同一来源给出的正面示例（**意译**） |

判据：读完前两句，读者是否已经知道"这篇在解决什么问题"或"结论是什么"。

### 3.2 断段（在转折处断）

| | 内容 | 出处 |
| --- | --- | --- |
| ❌ | 一整段：传统监控看请求和延迟，这对无状态 HTTP 服务够用；AI agent 不一样，一次运行可能有多次模型调用、工具执行和交接。 | 〔源〕该来源的反面示例（意译） |
| ✅ | 拆成两段，第二段以"AI agent 不一样"起句，前面留一个换行 | 〔源〕该来源的正面示例（意译） |

判据：转折点前是否有视觉停顿。来源明确说这个换行"在传统段落规则下是破格的"，但在线写作里是标准做法。

### 3.3 AI 写作的可识别特征（六对，均出自同一来源）

| | 反面 | 正面 | 出处 |
| --- | --- | --- | --- |
| a | 连续三段式短促断言："没有错误。没有告警。全是绿的。" | 合成一句正常叙述："没有错误，没有告警，一切看起来正常。" | 〔源〕意译 |
| b | 车贴式格言："你修不了你看不见的东西。" | 展开成有信息量的句子："如果看不见完整请求链路，你就是在猜。" | 〔源〕意译 |
| c | 三段式揭底："不是配置问题。不是代码 bug。是发布包旧了。" | 合成一句："既不是配置问题也不是代码 bug——发布包是旧的。" | 〔源〕意译 |
| d | 自作聪明的简约：贴完代码块紧跟一句"就这样，就这些。" | 贴完代码块后解释它做了什么，或直接往下走 | 〔源〕意译 |
| e | 广告式对仗："指标告诉你哪里坏了。链路告诉你为什么。" | 写成有主次的复句，而不是对仗 | 〔源〕意译 |
| f | **个性只在首尾**：个人化开头 → 80% 临床叙述 → CTA 收尾 | 人称旁白分布全篇（"这一步才是把我绊住的地方"） | 〔源〕意译 |

### 3.4 段标题

| | 内容 | 出处 |
| --- | --- | --- |
| ❌ | "背景" / "架构" / "结果" / "结论" | 〔源〕被来源直接列为弱标题的四个词 |
| ✅ | "为什么时序列预聚合会毁掉调试上下文" / "分布式 GROUP BY 的散播-聚集方案" / "它在哪里崩：基数墙" | 〔源〕同一来源的强标题示例（意译） |

### 3.5 数字与主张

| | 内容 | 出处 |
| --- | --- | --- |
| ❌ | "这显著降低了我们的错误处理时间。" | 〔源〕反面示例（意译） |
| ✅ | "这把 p99 错误处理时间从 340ms 降到 45ms，约 7.5 倍。" | 〔源〕正面示例（意译） |
| ✅（本骨架加强版） | "5.7｜RTX4090/32G｜场景X（资产A）｜基线120→148fps｜stat unit ×3 取中位｜原始数据 chart.csv" | 〔源〕`03_接口_v0.5.md` §4.5 的"到位"样例 |

**注意**：来源只要求"带数字"；第三行的六项条件是我们从 §4.5 的"能不能复现这次测量"推出来的（`WRT-TA-R05`，标注为推导）。

### 3.6 ⚠️ 来源内部自相矛盾的一处（必须两边都记）

| 面 | 内容 | 出处 |
| --- | --- | --- |
| A 面 | 排版规则明写：**不要用 em dash**，改用逗号、句号或换行；理由是 em dash 在博客排版里制造视觉杂乱 | 〔源〕该来源的排版节 |
| B 面 | 同一个来源在"技术质量标准"的**正面示例**里用了 em dash：`… from 340ms to 45ms — a 7.5× improvement.` | 〔源〕该来源的数字示例 |

**处理**：两边都记。规则表里 `WRT-TA-S02` 因此被定为**记录不阻断**——来源自己都没守住，我们没依据把它当阻断项。作者二选一，但同一篇内必须一致。

### 3.7 结尾

| | 内容 | 出处 |
| --- | --- | --- |
| ❌ | "我们等不及想看你能造出什么！" / 把全文复述一遍 / "试用 X，所有套餐都含。" | 〔源〕该来源直接列出的三种禁止收尾（意译） |
| ✅ | 回到开头那个故事；或给一个立刻能做的具体动作（文档链接、源码链接、反馈渠道） | 〔源〕该来源的正面做法 |

## 4. 常见失败模式（反模式清单）

按"被发现时最贵"排序。

| # | 反模式 | 为什么致命 | 对应规则 |
| --- | --- | --- | --- |
| 1 | **开头写背景/公司史/预告** | 浪费掉读者决定去留的唯一窗口 | `R01`、`S01` |
| 2 | **只讲"点哪个按钮"，不讲它怎么工作** | 文章失去存在理由；读者在自己产品的文档里也能看到 | `R02` |
| 3 | **不交代取舍与没选的方案** | 来源明说这是"好"与"极好"的分界；跳过它文章就只是公告 | `R03` |
| 4 | **深潜型不写试错与局限** | 读者会假定你藏了东西；而这两节恰恰是最能建立信任的 | `R04` |
| 5 | **性能主张只有形容词没有数字**；或者有数字但不可复现 | 前者是空话，后者是"结论在、数据不在"= 不可复现 | `S04`、`R05`、`S09` |
| 6 | **夸大能力**：把"建议了一个可能的根因"写成"找到了根因"；beta 不说 beta | 客户按文章做决定，落差由公司承担 | `R07` |
| 7 | **代码块跑不通 / 缺 import 与上下文** | 读者的第一动作就是复制粘贴 | `R06` |
| 8 | **企业腔与填充词**（宣布式开场、最高级自夸、空洞动词、空过渡） | 来源把它们列为"自动红旗"，且是 AI 生成物的典型指纹 | `S01` |
| 9 | **AI 味六征**：短促三连、格言体、三段揭底、自作聪明的简约、广告对仗、个性只在首尾 | 读者识别得比作者快；一旦识别，可信度归零 | `C08`、`R10`、§3.3 |
| 10 | **弱标题**：背景/架构/结果/结论 | 只看标题列表读不出内容；搜索里也不可见 | `S10`、`R08` |
