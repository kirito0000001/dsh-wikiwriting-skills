# 文体骨架：README

> 本文归属的规则：**WRT-RM-nn** ｜ 来源与许可见文末 §5
> 规则 ID 构成：`WRT-RM-<级别字母><两位序号>`。级别字母 = `S`(`structural_invariant`) / `R`(`reviewed_invariant`) / `C`(`craft_default`) / `T`(`taste_option`)，与 `规则契约.md` §0 的四级判定者表一致。
> 本文件是规则正文的**唯一处**：其它文件只许引 ID，不许复述条文（复述一次就有两处要同步）。
> **每条规范自带四字段**（接 `03_接口_v0.5.md` §9）：每条规则行末带 `〔源键｜依据类型｜版本与实施日期｜适用文体〕`；源键表见 §5.0。
> ⚠️ 纪律：以下所有条文都是**我们自己的话**。来源的逐字引用只出现在 §5，且每个来源 ≤1 句。

## 0. 适用与不适用

**用这个骨架**（条件）：产物是放在仓库根（或 `.github/`、`docs/`）的 `README.md`，读者是**路过的人**——他还不认识这个项目，要在 30 秒内判断"这是不是我要的东西"，并在 5 分钟内第一次跑出结果。

**不用这个骨架**（要求 → 换哪个骨架）：

| 情形 | 为什么不用 | 换成 |
| --- | --- | --- |
| 内容是"按步骤学会一门技能"的完整教学 | README 不是教程；教学要允许读者犯错并纠正 | 教程文档（Diátaxis 四类之一） |
| 内容是"我已经会用，现在要解决具体问题" | 这是工作导向，不是起步导向 | how-to / 故障排查文档 |
| 内容是完整 API 表、全部配置字段 | 参考材料的架构应反映被描述物的架构，README 装不下也不该装 | 参考文档 / `API.md` |
| 内容是设计决策的来龙去脉、为什么当初这么选 | 这是解释性材料，服务"理解"不服务"起步" | 技术文章 / ADR |
| 内容超过"起步与贡献所必需" | GitHub 官方立场：README 只放让开发者开始使用与贡献所必需的信息，更长的文档应放 wiki | wiki / 站点文档 |
| 仓库里没有功能代码（纯文档仓库） | 没有可安装、可导入的东西 | 仍用本骨架，但按 `WRT-RM-S02` 的例外豁免安装/用法两段 |
| 载体不是仓库根，而是 npm/PyPI 的项目页 | 项目页自己渲染 `description` 字段，与本骨架的一句话描述同源但展示位置不同 | 仍用本骨架，一句话描述按 `WRT-RM-S06` 与包管理器字段对齐 |

**必须先想清楚的一件事**：README 的**唯一职责是入口与分诊**，不是把四种文档揉成一份。Diátaxis 的立场是"边界被跨越或模糊，是大量文档问题的根源"——README 把教程、how-to、参考、解释全塞进去，就是这句话的教科书案例。

### 0.1 与采集侧的接口（`03_接口_v0.5.md` §7 / §9）

本骨架的每一条规则都必须能接上账本，否则写出来的正文不可复核：

- **§7 留痕** → 骨架里每一个结构判断（某段存在与否、某个数字、某个"支持 X"）都要能指回账本条目的 `A-nn`／`B-nn` ID。落实到 `WRT-RM-R11` 与 `WRT-RM-R12`。
- **§9 消费** → 正文里断言的**措辞强度**必须与该条在账本里的 `状态` 匹配（`一手已核` 直写／`自测` 必带测量条件／`二手线索` 必写"有报告称"／`待复审` 标"截至 <日期>"／`已推翻` 一律不得出现）。落实到 `WRT-RM-R10`。
- ⚠️ README 场景**额外加一道**：`§9` 只规定"怎么用已核的断言"，而 README 最常见的病是**把"有字段"当成"已实现"**。落实到 `WRT-RM-R08`（必须先证伪）。

## 1. 结构骨架（分节清单）

### 1.1 推荐序列（两来源合并后的 17 个位置）

"分歧"列的 `▲` 表示两来源给的位置/形态不一致，**不选边**，各自适用条件见 §2。

| # | 段 | 写什么 | 多长 | 为什么在这个位置 | 分歧 |
| --- | --- | --- | --- | --- | --- |
| 1 | **H1 标题** | 项目名（= 仓库名 / 目录名 / 包名）；不匹配时用"相关标题 +（斜体括号里的真名）" | 1 行 | 读者第一眼要确认"打开的是不是这个东西" | ▲ `WRT-RM-S14` ↔ `WRT-RM-C10` |
| 2 | **横幅 / Logo** | 仓库内本地图片，**本身不带标题** | ≤1 行 | 先给身份，再给信息 | 无 |
| 3 | **徽章** | CI / 版本 / 许可证 / 下载量 | 1–3 行 | 秒级可信度信号，必须在正文之前 | 无（banger 另加数量上限 → `S09`） |
| 4 | **一句话描述** | 干什么、给谁、替代了什么 | 独占一行，**无标题** | "值得我继续读吗"的唯一判断句 | ▲ 长度：`<120` ↔ `30–400` |
| 5 | **演示** | GIF / 终端录像 / 截图 / 最小可跑代码 | 1 段 + 1 张 | 展示代替陈述，**尽早在低成本处给价值证据** | banger 独有 |
| 6 | **功能亮点** | 3–6 条，每条一行 + 一句解释 | ≤8 行 | 让读者在安装之前判断能力边界 | banger 独有 |
| 7 | **快速开始** | 3–5 条可复制粘贴的命令，60 秒出结果 | 1 个代码块 | 最短成功路径，必须在详细安装之前 | banger 独有；standard-readme 无此段 |
| 8 | **目录** | 覆盖所有 `##`；不含标题与目录自身 | 自动生成 | ≥100 行时的导航；<100 行可省 | ▲ 位置：第 6 位 ↔ 第 7 位 |
| 9 | **长描述 / 背景** | 动机、抽象依赖、知识来源 | 2–4 段 | 读者先知道"是什么"，才会问"为什么" | 无（standard 拆成两段） |
| 10 | **安装** | 代码块；非常规依赖单列子段 | 按平台 | 到这一步读者才决定动手 | 无（文档仓库可豁免） |
| 11 | **用法** | 常见用法代码块；CLI 子段；可导入时给"导入 + 使用" | 2–5 个代码块 | 装完立刻能用 | 无 |
| 12 | **额外段** | 配置表、兼容矩阵、安全说明… | 自由 | 排"能用"之后、"查 API"之前 | 无（这段**不许**叫"额外段"） |
| 13 | **API** | 导出对象/函数、签名、返回、caveat；**或只放一个指向 `API.md` 的链接** | 可极短 | 参考材料，按需查 | 无 |
| 14 | **维护者** | 该被 ping 的人 + 一种联系方式 | ≤5 行 | "出问题找谁" | 无 |
| 15 | **致谢** | 显著帮助过项目的人/物 | ≤10 行 | 归属 | ▲ 位置：License 之前 ↔ License 之后 |
| 16 | **如何贡献** | 在哪提问、收不收 PR、贡献要求 | ≤10 行 | 接住"我想帮忙"的冲动 | 无（standard 记为**必需**） |
| 17 | **许可证** | SPDX 标识符 + 许可证所有者 + 指向 `LICENSE` | 1–3 行 | —— | ▲ `WRT-RM-S04`（必须最后）↔ banger 让致谢占了最后一位 |

**顺序理由（一句话）**：整份 README 走**认知漏斗**——从"这是什么"（1–4）→"它能干什么"（5–6）→"我要怎么用上它"（7–13）→"坏了找谁"（14）→"法律许可"（17）。越靠前的段服务越多的读者，越靠后的段服务越少的读者。**让不合适的读者在低成本的早期就离开，是这个顺序的主要收益，不是副作用。**

### 1.2 与其它文档的分工（Diátaxis）

README 本身**不是** Diátaxis 四类之一；它是**入口与分诊台**。分工按下表判定：

| 读者此刻在干什么 | 属于哪一类 | 该写在哪 |
| --- | --- | --- |
| 在学技能，需要有人带着走一遍 | 教程（行动 + 习得技能） | 不看 README。单独的教程文档 |
| 已经会用，要完成一件具体的工作 | how-to（行动 + 应用技能） | README 最多给**一条**最常见的，其余链接出去 |
| 要用得正确，需要准确完整的描述性事实 | 参考（认知 + 应用技能） | `API.md` / 站点参考页。README 只放链接 |
| 想理解为什么、放进更大的图景 | 解释（认知 + 习得技能） | 技术文章 / 设计文档。README 的背景段只放**最小动机** |

**反向义务**：README 必须**明写这些指针**。"快速开始"点向教程，"配置"点向参考，"背景"点向解释——读者不需要猜。

⚠️ Diátaxis 同一页里还有一句必须一起执行的约束：**不要为了四类各建一个空结构**。所以**不许**在 README 里留下"教程（待补）"这种空壳段（→ `WRT-RM-S10`、`WRT-RM-R03`）。

### 2.2 `reviewed_invariant`（凭证据判，reviewer 判定）

| ID | Class | Knowledge |
| --- | --- | --- |
| `WRT-RM-R01` | reviewed_invariant | 条件是准备把某段内容写进自述文件 → 要求该内容属于"让读者开始使用与贡献所必需" → 例外：更长的内容以 wiki / 站点文档承载；判定时要**引证据**说明该内容为什么属于"起步必需"，不许凭"我觉得有用"。 〔GH｜官方文档｜main·抓取 2026-10-07｜README〕 |

## 3. 正反例

出处标注规则：`〔源〕` = 直接来自某来源；`〔自造〕` = 本轮据某条规则构造，**非源文**。示例一律为意译/译写，**不是**来源的逐字原文。

### 3.1 一句话描述

| | 内容 | 出处 |
| --- | --- | --- |
| ❌ | `> 一个非常强大的、业界领先的现代化工具，可以无缝地赋能你的工作流。` | 〔自造〕据 `WRT-RM-S05`（不以 `> ` 开头）与来源明确列为红旗的禁用词 |
| ✅ | `**rmb** is a CLI for building and rating great READMEs.` | 〔源〕banger-readme 的模板句式（这是它给出的模板填充样例） |

判据：读者读完这一行，能不能说出"给谁、干什么"。说不出来就是 ❌。

### 3.2 H1 标题（两来源直接冲突，故给两组）

| | 内容 | 出处 |
| --- | --- | --- |
| ✅（合规派） | `# Standard Readme Style _(standard-readme)_` | 〔源〕standard-readme 给出的示例 |
| ❌（合规派） | `# 我的项目`——而仓库名是 `my-project`，且长描述里没解释为什么不匹配 | 〔自造〕据 `WRT-RM-S14` 的例外条款 |
| ❌（转化派） | 顶部先写一个与仓库名逐字相同的 H1，紧跟着搜索框里已经显示过同样的名字 | 〔源〕banger-readme 把"与仓库名相同的 H1"列为反模式 |
| ✅（转化派） | 顶部直接放 Logo 图，跳过 H1 | 〔源〕banger-readme 的替代做法 |

### 3.3 段标题

| | 内容 | 出处 |
| --- | --- | --- |
| ❌ | `## 背景` / `## 架构` / `## 结果` / `## 结论` | 〔源〕空词闭集来自技术文章侧同一来源的段标题清单，**定义在 `文体-技术文章.md` 的 `WRT-TA-S10`**（不在此处重复定义）；README 侧的适用见 `WRT-RM-C09` |
| ❌ | `## 简介` 后面直接跟下一个标题 | 〔自造〕据 `WRT-RM-S10` |
| ✅ | `## 这个是干什么的（30 秒判断要不要用）` | 〔自造〕据 `WRT-RM-S13`／`WRT-RM-S03`：功能性保留段名（安装/用法/许可证）不改写，其余标题要传达信息 |

### 3.4 演示素材

| | 内容 | 出处 |
| --- | --- | --- |
| ❌ | 一张精心渲染的 UI 概念图，实际程序还没有这个界面 | 〔自造〕据 `WRT-RM-R05` |

## 4. 常见失败模式（反模式清单）

按"被发现时最贵"排序。

| # | 反模式 | 为什么致命 | 对应规则 |
| --- | --- | --- | --- |
| 1 | **把 README 写成四类文档的合集**：教程、完整 API 表、设计决策全塞进来 | 边界模糊是文档问题的头号成因；且把起步读者淹死 | `R01`、`R02` |
| 2 | **空壳结构**：为"教程/how-to/参考/解释"各留一个"（待补）" | 来源明确点名这种做法"很糟"；读者看到的是承诺而非内容 | `R03`、`S10` |
| 3 | **占位符交付**：`Coming soon` / `TODO` / 空段 | 空段必须整段删掉，不是填占位 | `S10` |
| 4 | **一句话描述与包管理器字段、平台描述三处各写一份** | 三份描述迟早互相矛盾，而读者会同时看到其中两份 | `S06` |
| 5 | **快速开始里的命令没人跑过** | 读者的第一次体验失败，之后不会再给第二次机会 | `R04` |
| 6 | **"支持 X"只凭配置里有这个键** | 有字段 ≠ 有实现 ≠ 默认开 | `R08` |
| 7 | **正文数字/断言无法回指账本** | 无法复核 = 不可交付；这条也是"AI 味"的真正来源 | `R11` |
| 8 | **措辞强度超过账本状态**：把 `二手线索` 写成确定结论 | 违反 §9 消费规则；读者按它做了决定，错在文章 | `R10` |
| 9 | **演示素材是渲染图而非运行结果** | 用示意冒充事实，读者试用时落差巨大 | `R05` |
| 10 | **长文无目录 / 依赖平台 Outline** | 换到 npm、编辑器、镜像站点上就没有 Outline 了 | `S07`、`C03` |
| 11 | **徽章滥用**：一行十几个、堆三行 | 首屏被无信息量的图占满 | `S09` |
| 12 | **全大写段标题** | 视觉噪音，且破坏段名闭集 | `S13`、`S11` 相邻约束 |
| 13 | **图片无 alt** | 无障碍问题，且图片挂掉后段落语义丢失 | `S12` |
| 14 | **超长单文件**（>2000 行） | 详细内容应移出到独立文档 | `R01`、`S09` |
| 15 | **自称合规却静默偏离 standard-readme** | 比不自称更糟：校验者会信你 | `R12` |
| 16 | **`安装`/`用法` 排在 `一句话描述` 之前** | 违反漏斗：读者还不知道这是什么就被要求动手 | `S03`、`C01` |
