# dsh-wikiwriting-skills

**dsh-wikiwriting-skills** 是一套给 DSH 用户的写作技能，它让 AI 写出来的每一句都能翻回材料出处。

## 一条素材条目长什么样

这套技能的全部价值在《素材账本》里。下面是**两条真实条目**，
**照原样抄自一次实际采集（未删任何字段）**：

```
**A-05**｜状态：一手已核｜断言：技能有**五个**默认加载根，按 rank 扫描；**装一次给所有项目用**是
  rank 400 的 `<dshHome>/skills`（`dshHome` 默认 `$DSH_HOME` 或 `~/.dsh`），**只给一个项目用**
  是 rank 100 的 `<项目根>/.dsh/skills`
  - 定位：`D:\NewData\deepseek\DSH Desktop\resources\app\node_modules\
          @deepseek-ai\dsh-skill-filesystem\README.zh.md:44-56`
  - 引用路径：`dsh_fs[根目录与优先级]`
  - 证据：小节「根目录与优先级」的表格列出 100 `project-dsh`／200 `project-agents`／
          300 `custom`／400 `user-dsh`／500 `user-agents`
  - 钉死：工作区@2026-10-07 ｜复审周期：90d ｜失效条件：DSH 改加载根或 rank
  - 检查方式：看 该文件:44-56

**B-06**｜状态：二手线索｜断言：AI Act Article 50 要求 AI 生成或操纵的内容**可标记、可检测为人工生成**
  - 定位：`https://ai-act-service-desk.ec.europa.eu/en/ai-act/article-50`
  - 影响：→ 页面 200 但**是导航页，条文正文未取到** → 正文只能写「有报告称」
  - **矛盾**：`A-04`（同一 URL，一条已核一条未核）→ 见 `#### 未决`
```

（上面两条的**换行**是为了放进代码块而加的，字段一个字没改。）

**两条的区别就是这套技能的全部主张**：
`一手已核` 的可以直接写进正文，`二手线索` 的**必须降级措辞**；
写正文时，每个数字后面挂一个角标回指账本条目，
**翻不回去的句子不许交付**。

## 三个技能：检索 → 采集 → 成文

| 技能 | 干什么 | 说什么话会触发 |
| --- | --- | --- |
| **`zhihu`** | 动手前先查别人走过的路：多轮检索 → 统一研读 → **自己验证** | 「先搜集资料」「研究一下」「查一下原因」 |
| **`wiki-collect`** | 把一手材料读成《素材账本》—— 每条带**可回溯定位、够核对的证据、能判真假的状态** | 「先采集素材」「读一遍这个仓库，把能用的挑出来」 |
| **`wiki-write`** | 把账本写成别人看得懂的成稿：README／技术文章／设定集／剧本／小说 | 「帮我写一篇」「写个 README」「这段读起来不清楚」 |

三者**靠文件交接，不共享内存**：上一个技能的产物就是下一个技能的输入。
拆成三个而不是一个，是因为三者的**交集几乎为零**（检索 ≠ 提取 ≠ 组织表达）。

## 它能写哪五种东西

`wiki-write` 带**五套文体骨架**，各管一种产物，**一次只加载一套**。
它不是 README 生成器 —— 下面五种都是它的活：

| 写什么 | 产物 | 读者此刻在干什么 |
| --- | --- | --- |
| **README** | 仓库根（或 `.github/`、`docs/`）的自述文件 | 路过的人，**30 秒**内判断"这是不是我要的东西" |
| **技术文章** | 工程博客、技术号、内部分享长文 | 同行工程师，在**滚动信息流**里决定点不点 |
| **设定集条目** | 游戏设定 wiki：人物／地点／势力／时间线／术语／数值 | 多数时候**就是作者自己与团队**：策划／文案／美术／程序／QA／本地化 |
| **剧本** | 影视剧本的正文格式与结构；舞台剧**部分**；游戏分支对白脚本 | 读剧本的人，要能一眼分清场景、动作、对白 |
| **小说** | 长篇／短篇／连载网文、游戏内叙事文本 | 读者，要的是**排版与一致性**不崩 |

五套骨架是一份份独立文件（`文体-README.md` · `文体-技术文章.md` · `文体-设定集.md` ·
`文体-剧本.md` · `文体-小说.md`），所以**每篇真正"必须过"的第一级规则是 10–24 条**，
不是几百条一起上。

## 快速开始

> **前提**：你已经在用 **DSH**。这三个是 DSH 技能，没有 DSH 就没有加载器。

在**仓库根目录**执行（就是你 clone 或下载下来的那个目录）：

```powershell
# 装进 DSH 的用户技能根（装一次，所有项目可用）
New-Item -ItemType Directory -Force -Path "$HOME\.dsh\skills" | Out-Null
Copy-Item -Recurse -Force .\wiki-collect, .\wiki-write, .\zhihu "$HOME\.dsh\skills\"

# 确认装好了：三个工具都要能跑起来
node "$HOME\.dsh\skills\wiki-collect\tools\check.mjs" --implemented
node "$HOME\.dsh\skills\wiki-write\tools\check.mjs"  --selftest
node "$HOME\.dsh\skills\wiki-write\tools\publish.mjs" --selftest
```

**上面三条命令在本机实跑过**，输出即下面这段（Windows / PowerShell，node v24.16.0，2026-10-07）：

```
implemented: 15 条
COL-S01 COL-S02 COL-S03 COL-S04 COL-S06 COL-S07 COL-S09 COL-S10 COL-S11 COL-S12 COL-S14 COL-S17 COL-R01 COL-R04 COL-R12
selftest: OK（68 项断言，64 个夹具）
selftest: OK（28 项断言，13 个夹具）
```

复制是**幂等**的：跑完前后三个技能目录的文件数与字节数完全相同，技能目录的 `git status` 仍为空。

⚠️ **第一条为什么用 `--implemented` 而不是 `--selftest`** —— 这是我们实跑时撞到的：

`wiki-collect/tools/check.mjs --selftest` **跑完自检不会停**，它还会拿**当前目录**当专题再查一遍。
于是从仓库根执行会看到 `found N (major=1)`（内容是「找不到 `01_素材账本.md`」），
**并以退出码 1 结束**。**那不是安装失败** —— 另外两个工具会正常停。

**不需要重启 DSH** —— 技能监视是默认开的，新增／改名／删除会被自动发现。

## 它解决什么问题

**AI 写出来的东西，读起来通顺，但你问不出「这句话哪来的」。**

这不是措辞问题。一份交代不清来源的稿子，**别人没法复核，也没法反驳** ——
它能用只是因为暂时没人查。而真正要给别人看的东西（README、技术文章、设定条目），
恰好都是**会被查**的东西。

这套技能的答案很笨：**先建账本，再写正文。**
`wiki-collect` 把材料逐条读成可回溯的断言，`wiki-write` 只许写账本里有的，
正文里每个数字都挂角标回指账本条目。上面那条素材条目就是它的产物。

**它不保证说得对。** 它保证的是：**说得对不对，你能查。**
账本里的 `状态` 描述的是「我拿到一手来源、逐字核对过它确实这么说」，
**不是「世界上确实如此」**。这两件事分得开，才谈得上复核。

## 安装

### 装到哪：五个默认加载根，按 rank 扫描

| Rank | 来源 | 路径 | 什么时候用 |
| --- | --- | --- | --- |
| 100 | `project-dsh` | `<项目根>/.dsh/skills` | **只给某一个项目用**（优先级最高） |
| 200 | `project-agents` | `<项目根>/.agents/skills` | 同上 |
| 300 | `custom` | 配置项 `customSkillDirs` | 自定义 |
| **400** | **`user-dsh`** | **`<dshHome>/skills`** | **装一次给所有项目用** |
| 500 | `user-agents` | `<agentsHome>/skills` | 同上 |

- `dshHome` 默认是 `$DSH_HOME` 或 **`~/.dsh`**
- ⚠️ **`<项目根>` = 含 `.git` 的最近祖先目录**；不存在则用当前工作目录

### 装成什么形态：两条都合法

- **目录 bundle**：`<技能名>/SKILL.md` ← **这个仓库里的三个都是**
- **平铺文件**：`<技能名>.md`

⛔ **刻意不支持嵌套的 `**/SKILL.md`**。
`~/.dsh/skills/my-skills/wiki-collect/SKILL.md` **不会被发现** ——
**别为了整理目录多套一层。**

### 三个会让人「装上了却用不了」的坑

1. **`name` 不合规 = 整条技能被静默忽略**。
   它必须匹配 `^[a-z0-9]+(?:-[a-z0-9]+)*$`（小写字母、数字、单连字符）。
   ⚠️ 不会报错，日志里只有一行 `ignored: invalid skill name`。
2. **frontmatter 里只有六个字段会被读到**：
   `name` · `description` · `whenToUse` · `disable-model-invocation` · `user-invocable` · `metadata`。
   **其它一切静默忽略** —— 写 `license:` 没人读得到。
3. **`description` 缺失 = 整条技能不加载**。它是路由依据，不是注释。

## 用法

三个技能**按顺序用**，中间产物落在你自己的专题目录里：

```
zhihu          检索  →  别人走过的路（外部资料）
  ↓
wiki-collect   采集  →  00_选题卡 · 01_素材账本 · 03_变更与缺口
  ↓
wiki-write     写作  →  04_草稿 →（机检）→ 06_发布版
```

一次典型对话 —— **三种活各一例**：

```
你：先搜集资料，我要给这个仓库写 README      → zhihu 起手，建候选清单，自己验证链接
你：用 Collect 日常档看技能内部               → wiki-collect 建账本，每条带定位与状态
你：写 README，包括安装和使用                 → wiki-write 出 04_草稿 →（机检）→ 06_发布版

你：读一遍这个剧本，把能用的挑出来             → wiki-collect 走虚构类：账本 + 02_设定表
你：把这份素材写成文章                        → wiki-write 按「文体-技术文章」成文

你：把这些设定整理成能引用的                  → wiki-collect 走设定集：人物／地点／势力逐条落定位
你：写设定条目                               → wiki-write 按「文体-设定集」成文
```

**素材从哪来**：代码仓库、剧本与设定、你自己的旧稿、实验数据。
**技术专题和虚构类走同一条流水线**，只是字段侧重不同 —— 虚构类会多出一份 `02_设定表.md`。

## 一次运行要交几个文件

两个技能都有**日常档**和**改进档**两档，**默认日常档**：

| | **日常档**（默认） | **改进档**（技能作者本人改技能时才用） |
| --- | --- | --- |
| **采集侧** | 只做采集 | 再加复盘与技能反馈 |
| **写作侧交几个文件** | **两个**：`04_草稿.md` ＋ `06_发布版.md` | **四个**：再加 `05_复述测试.md` ＋ `07_交付说明.md` |
| **跑复述测试吗** | 不跑 | **跑，2–3 轮** |

⛔ **日常档不等于"随便写"** —— 这几条照旧必做：

```powershell
node tools/publish.mjs --draft  04_草稿.md                # 生成 06_发布版.md
node tools/publish.mjs --verify 04_草稿.md 06_发布版.md    # 必须逐字节相同
node tools/check.mjs --file 06_发布版.md --genre readme
```

**改稿只改草稿，然后重跑转换。永远不要直接编辑 `06_发布版.md`。**

## 这个仓库还差什么

**这几条技能自己就写着，这里照实转述**：

- `wiki-write` 的 88 条 `structural_invariant` 里，**只有 15 条有执行者（约 17%）** ——
  所以 **`check.mjs` 全绿 ≠ 文稿合规**，不得声称「第一级规则已过」
- **剧本／小说两类零实战** —— 116 条规则从没在真实材料上跑过
- **复述测试全部由 AI 实例完成** —— 人类那条路实际走不通
- **`wiki-collect` 的必读集已超预算**（虚构类只剩不到 1 KB 余量）
- **规则是靠"撞"长出来的**，不是设计完整了才发布 —— 所以它一定还有没撞到的洞

⭐ **而最该记住的一条来自它自己的方向体检**：

> **推演出来的规则总有洞。**
> **「精度不取决于算法，取决于语料里有没有教语法用的例子。」**

## 里面有什么

```
dsh-wikiwriting-skills/
├── wiki-collect/     SKILL.md + 9 份 references + tools/check.mjs
├── wiki-write/       SKILL.md + 9 份 references（**含 5 套文体骨架**）+ tools/（3 份）
├── zhihu/            SKILL.md
├── README.md         ← 你正在读的（面向使用者）
├── 制作过程.md        这套技能是怎么做出来的（面向学习者）
└── 对接文档.md        下次改进这套技能从哪接手（面向技能制作方）
```

**三个技能各自带可跑的检查器**—— 它们守的是**规则表自身的完整性**与**发布不变式**，
不守文稿的语义：

```powershell
node wiki-collect\tools\check.mjs --topic <专题目录> --base <被采仓库根>            # 查账本
node wiki-write\tools\check.mjs  --file 06_发布版.md --genre readme|wiki|tech      # 查成稿
node wiki-write\tools\check.mjs  --topic <专题目录>                                # 查专题级产物
```

⛔ **这些工具是拿来跑的，不是拿来读的** —— 跑一次看输出，比读源码便宜两个数量级。

**想学它是怎么做出来的**（28 轮改动、一张"反复犯过的错"表、一条被脚本误删又恢复的规则），
读 [`制作过程.md`](制作过程.md)。**那份文档讲方法，不记流水账。**

## 如何贡献

**这个仓库是自用项目，没有承诺的维护节奏，不保证合并 PR。**

如果你在用这三个技能时撞到了问题，**最有价值的贡献不是改代码，是留一份反馈**：

两个技能都会在跑完之后要求你写 `<专题目录>/_work/技能反馈.md`——
**只记事实、不写建议**。判据是一个问句：

> **这次运行里，有没有哪一步是「靠你自己的判断补上的」？**

这类记录是这套技能唯一的质量来源：**它的规则全是撞出来的**。
