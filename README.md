# dsh-wikiwriting-skills

三个给 [DSH](https://github.com/deepseek-ai) 用的技能。它们串成一条流水线：**把一手材料变成别人看得懂的成稿。**

| 技能 | 一句话 | 什么时候它会自己跳出来 |
| --- | --- | --- |
| **`wiki-collect`** | 读一手材料，产出**每条都带出处**的素材账本 | 「先采集素材」「把这些材料整理成能引用的」「给我建素材账本」 |
| **`wiki-write`** | 把账本写成**别人看得懂**的成稿 | 「帮我写一篇」「写个 README」「这段读起来不清楚」「帮我改稿」 |
| **`zhihu`** | 动手前先查别人走过的路 | 「研究一下」「调研一下」「先搜集资料」「查一下原因」 |

---

## 为什么需要它

### 问题一：AI 写的东西**追溯不到出处**

这不是印象，是有研究记录的现象：

- 微软研究院的 **VeriTrail** 专门做这件事 —— 检测**多步 AI 工作流**里的幻觉、并**追踪内容到它的来源**。
  它的开场问题就是：「这些应用的一个关键挑战是，模型可能产出**源文本并不支持**的内容。」
  （见来源 1）
- 语言模型「在预训练时学到了大量知识，但**往往不知道这些知识的来源**」——
  这是 arXiv 上 *Source-Aware Training* 那篇的原话。（见来源 2）
- 更麻烦的是**幻觉引用**：它「看起来是真的，把真实元素和编造元素混在一起，
  但对应不到任何真实来源」—— 大学图书馆为此专门写了指南。（见来源 4）

**`wiki-collect` 就是冲这个来的。** 它的账本每一条都必须带：

| 字段 | 作用 |
| --- | --- |
| `定位` | **这条断言从哪来** —— `文件:行` / `URL` / 符号名（只许这四种形态） |
| `证据` | **够核对的最小片段** —— 不是整段抄，是"你要能自己去核" |
| `状态` | **它是怎么来的** —— `一手已核` / `自测` / `二手线索` / `待复审` / `已推翻` |
| `钉死` | **在哪一版看到的** —— commit hash / tag / 快照日期 |

**→ 一句断言说得再漂亮，**指不到位置就不许进账本**。**

### 问题二：**"有出处"不等于"别人看得懂"**

这两件事经常被混为一谈，而它们**需要不同的检查手段**：

- **规则对不对** —— 机器能查（格式、悬空引用、数值自洽）
- **人看懂没有** —— **机器查不了**

**这个项目自己撞过最典型的一次**：一份成稿里藏了一个 `U+0008`（退格符），
位置在 `Windows ` 与 `.0.17763.0` 之间。

- **编辑器里完全看不见**
- **读者看到的是"少了一个 `1`"**
- **三轮机械检查都没抓到**（它不报错、不显形）
- **是两轮"复述测试"独立命中的**

**→ 所以 `wiki-write` 的验收用的是「零上下文复述测试」**：找一个新的读者实例，
**只给它一份成稿**（不给账本、不给背景），让它复述 ——
**它提的是细节问题还是基本问题，直接说明这篇写清楚没有。**

### 问题三：AI 写长东西会**跑丢**

一个真实的数字：这个项目有一轮让 AI 跑完整链路（采集 → 成文 → 验收），
结果它跑到 **917K token，撞了上下文上限，一个字都没落盘。**

**→ 所以两个技能都写明了**硬预算**（技能加载只读路由给的那一两份、子代理最多 2 个、总轮次 ≤10），
并把「你发现自己在读第三个技能文件」定义成**要报告的问题**，而不是"我再多读点就好了"。

### 治理层也要这个

「缺少来源追溯时什么会坏」这个问题，已经有标准框架在管：

- **NIST CSF 2.0**（`GV.RM-01`）—— 溯源是 AI 治理的一部分，风险决策要可追溯
- **NIST AI RMF**（`GOVERN`）—— 治理要求透明、问责、可追溯
- **OWASP Agentic AI Top 10**（`LLM-06`）—— 幻觉相关

（见来源 3）**→ 可追溯不是"讲究"，是要求。**

## 怎么装

DSH 会扫描**五个**技能根目录，按优先级（rank 数字小的先）：

| Rank | 来源 | 路径 |
| ---: | --- | --- |
| **100** | `project-dsh` | **`<项目根>/.dsh/skills`** |
| 200 | `project-agents` | `<项目根>/.agents/skills` |
| 300 | `custom` | 配置项 `customSkillDirs` |
| **400** | `user-dsh` | **`~/.dsh/skills`** |
| 500 | `user-agents` | `~/.agents/skills` |

> ⚠️ **`<项目根>` 指的是「含 `.git` 的最近祖先目录」**；找不到就用当前工作目录。

### 装法一：全局（推荐）

**三个技能都给所有项目用** —— 复制到用户根：

```powershell
git clone <这个仓库的地址> $env:TEMP\dsh-wikiwriting-skills
foreach ($s in 'wiki-collect','wiki-write','zhihu') {
  Copy-Item "$env:TEMP\dsh-wikiwriting-skills\$s" "$HOME\.dsh\skills\" -Recurse -Force
}
```

### 装法二：只给一个项目用

```powershell
foreach ($s in 'wiki-collect','wiki-write','zhihu') {
  Copy-Item "<仓库路径>\$s" "<你的项目>\.dsh\skills\" -Recurse -Force
}
```

### 装完怎么确认

**DSH 会**自动发现**新增的技能 —— **不需要重启**（这一点和插件不同）。**
新开一个对话，说「先采集素材」，看它有没有反应。

### ⛔ 两个容易装错的地方

1. **不能塞进子目录。** 技能必须是 `<技能名>/SKILL.md` 这种**一层**结构 ——
   `~/.dsh/skills/my-skills/wiki-collect/SKILL.md` **不会被发现**。
2. **技能名不能乱改。** 目录名必须匹配 `^[a-z0-9]+(?:-[a-z0-9]+)*$` ——
   **写成 `Wiki-Collect` 会让整条技能被静默忽略**（日志里只有一行 `ignored: invalid skill name`）。

## 怎么用

### ⭐ 两种档：日常档（默认）与改进档

**日常用，只走两步：采集 + 书写。** 复盘那套（复述测试、技能反馈）**是给技能作者改进技能用的，不是日常必需**。

| | **日常档**（默认） | **改进档**（技能作者专用） |
| --- | --- | --- |
| **做什么** | **只做采集 + 书写** | 再加**复盘**（复述测试）与**技能反馈** |
| **交几个文件** | ⭐ **两个**：`04_草稿.md` ＋ `06_发布版.md` | 四个：再加 `05_复述测试.md` ＋ `07_交付说明.md` |
| **要跑复述测试吗** | ⛔ 不用 | ✅ 要，2–3 轮 |

**⛔ 但"日常档"不等于"随便写"** —— 这三条照旧必做，因为它们都只是**一条命令或一次判断**：

- **发布不变式**：`publish(草稿) ≡ 发布版`，逐字节相同
- **成稿级检查**：一条命令，查格式与结构
- **落地声明**：成稿**要落进某个既有位置**时，写清目标路径、那个位置的既有约定、和既有页的关系

### 一次典型的日常使用

```
你：把 D:\SomeRepo 的 README 写一下
   ↓
wiki-collect   读仓库 → 01_素材账本.md（每条带 文件:行 + 证据 + 钉住版本）
   ↓
wiki-write     账本 → 04_草稿.md → 06_发布版.md
   ↓
你：拿到 06_发布版.md
```

### 需要"别人真的看得懂"时

**给它找一个**不知道背景的人**（或者一个新的 AI 实例），**只给成稿**，让他复述。**
问一句话就够：

> **他提的问题是「细节」，还是「基本面」？**
> **问细节 → 这篇基本过关；还在问基本面 → 没写清楚，回去改。**

### 需要外部资料时

**`zhihu` 管这个** —— 它是三个里唯一**联网**的。说「先搜集资料」「调研一下」就会触发它。
⚠️ **它检索到的东西，请落成一个文件**（比如 `_src/原理-主题.md`），**再交给 `wiki-collect` 当材料采** ——
**只在对话里的检索结果，下一个会话看不到。**

## 它们怎么配合

```
zhihu          检索   →  别人走过的路（外部资料）
  ↓
wiki-collect   采集   →  素材账本 + 设定表 + 缺口清单
  ↓
wiki-write     写作   →  成稿
```

**三个技能靠**文件**交接，不靠共享上下文。** 所以你可以只用其中一个：
只想整理材料就只用 `wiki-collect`；材料已经有了就直接 `wiki-write`。

**为什么拆成三个而不是一个**：三者的**交集几乎为零**（检索 ≠ 提取 ≠ 组织表达），
拆开就不会出现"同一套规则被复制多份、然后互相漂移"。

---

## 它不做什么

**`wiki-collect`**：不写正文、不排版发布、**不做网络检索**（那是 `zhihu` 的活）、不做终审。
**`wiki-write`**：不负责采集素材 —— **输入应该是 `wiki-collect` 的产出**。

## 边界（诚实版）

**这几条技能自己就写着，这里照实转述：**

- **`wiki-write` 有 88 条 `structural_invariant`，只有 15 条有执行者。**
  其余的**靠人核**，机器查不了。
- **`check.mjs` 全绿 ≠ 文稿合规。** 技能自己写着这句 —— 不得声称"第一级规则已过"。
- **剧本与小说两类零实战**（116 条规则从没在真实材料上跑过）。
- **复述测试全部由 AI 实例完成。** 人类那条路实际走不通 —— 时间盒那一类判据对机器实例记 `N/A`。
- **规则是靠"撞"长出来的，不是设计完整了才发布。** 所以它**一定还有没撞到的洞。**

**⭐ 这个项目最值钱的一条经验，写在 `制作过程.md` 里：**

> **推演出来的规则总有洞。**
> **「精度不取决于算法，取决于语料里有没有教语法用的例子。」**
