# 冲突裁决（多源相争时怎么办）

> 适用信号：两条来源对同一件事给出不同说法；或怀疑是 **date／scope 差异**（不同时间、不同范围）。
> 规则级别见 `规则契约.md`；本文只引 ID。
> **这是整个流程最贵的一步**，预留时间，别把它排到最后。
> 本文**归属**的规则：`COL-R10` `COL-R27`；**引用**的：`COL-S06` `COL-R08` `COL-R21` `COL-C05`。

---

## 1. 先接受一个事实

**三条实测冲突，没有一条是「找不到」。** 全都白纸黑字、语气确定 —— 你必须回**第三个源**才能定案。
所以：**冲突 ≠ 有一方在骗人。** 绝大多数冲突的真实成因是：

| 成因 | 长什么样 |
| --- | --- |
| **date 差异** | 同一份内容在两个时间点的两个说法；实现已经跟进，提案文本没改 |
| **scope 差异** | 一个说「支持 X」，另一个说「不支持 X」—— 其实一个说的是默认关、一个说的是可开启 |
| **身份差异** | 两个名字是不是同一个东西，还没归一化 |
| **层级差异** | 一个说代码意图、一个说实际生效的配置 |

**先归类，再裁决。** 归不出类的，进缺口清单，**不许二选一蒙**。

---

## 2. 裁决顺序（实测有效）

```
补丁 / 产物  >  代码  >  提交历史  >  README 散文  >  docs/ 提案
```

| 位置 | 排这里的理由 |
| --- | --- |
| **补丁／产物** | 排在最前：**实际生效的配置比代码意图更接近事实** |
| **代码** | 真实实现 |
| **提交历史** | 见 §3 —— 两源相争时的强制一步 |
| **README 散文** | 面向人的叙述，可能滞后 |
| **`docs/` 提案** | **排最后：它是提案，不是实现** |

⚠️ **`docs/` 排最后的依据是实测**：两条错结论**都出自 `docs/`**，而且**是同一种成因** —— 「实现已经跟进，提案文本没改」。
→ **凡是 `docs/` 与代码／产物冲突，默认不信 `docs/`**；要信它，必须拿出「提案已经落地」的证据（`COL-R27`）。

---

## 3. 硬规则：两源相争，必看提交历史（`COL-R10`）

**只要两条正经来源对不上，就先查历史，不要直接选一个。** 实测有 **3 次**是靠提交历史定案的。

**做法**（命令形态只是建议，能拿到同样的信息即可）：

1. 找这两份文件各自的最近改动：`git log -n 5 --date=short -- <文件>`
2. 看时间关系：**提案与实现的改动是不是同一天？**
3. 看内容关系：`git log -p --follow -- <文件>`，找改动前后的差异。

**最值钱的一次发现**：**提案与修订发生在同一天，而提案文本没跟着改** —— 光看两份文件看不出任何异常，只有比时间才发现。

⚠️ 注意区分：`git log` 与你手上的 `钉死`（commit hash）不是一回事。`钉死` 记录「我是在哪一版看到的」，`git log` 用来判「谁先谁后」。

### 3.1 ⛔ 材料**不在任何 VCS 里**时怎么办（v0.5 补 —— 实测撞出来的）

**先向上找最近的 VCS 根。** 材料在被采仓库的**子目录**里时，子目录自己没有 `.git`，**外层仓库有** —— 那就是你的历史。实测一轮只查了子目录、判定"材料不是仓库"，**白白放弃了这条强制步骤**。

**确实没有 VCS 时**（散文件、导出稿、`.docx`、没有外层仓库的目录），按这个顺序退：

| 退路 | 能判什么 | 判不了什么 |
| --- | --- | --- |
| ① **文件 mtime** | 谁后改的 | 改的人是不是"更新"（可能只是修错字） |
| ② **内容里的日期**（页脚、frontmatter 的 `source_updated`） | 材料**自称**的版本时间 | 自称可能是错的 |
| ③ **文件名／目录里的版本号** | 有编号体系时的先后 | 编号体系本身可能没定义 |

⛔ **三条都拿不到先后时，不许猜。** 照实写「两稿并存，**无法判先后**」，进 `#### 未决`，并在缺口清单里说明**为什么判不了**（哪一条退路试过、结果是什么）。

⚠️ **`COL-R10` 说的是"必看"，不是"必能定案"。** 看过了、判不了，如实记 —— **那本身是一个合格的结论**，比选一个然后不说理由强。

## 4. 处置：写进哪里

| 情况 | 处置 |
| --- | --- |
| 定案了，结论唯一 | 断言按新结论写，`钉死`／`定位` 指到定案的那个源（**不是**被否掉的那个） |
| 定案了，且这是「曾冲突、已解决」 | `矛盾` **三态里的 `已解除`** + `#### 未决` 小节里写清**解除条件**；**条目保留不删**（`COL-R08`） |
| **跨版本冲突**（实现跟进、`docs/` 没改） | **算矛盾**（属 date/scope 差异），**必须显式解除**；否则 `未决` 会永久沉淀一堆其实已解释清的项 |
| 裁不了 | 进**缺口清单第三类**：写**双方 + 各自出处**，不许只写「有冲突」 |
| 你发现其中一条其实说错了 | 那条标 `已推翻`（留着），并在 `#### 未决` 里写明推翻理由和出处 |

**双轨不能只做一半**（`COL-S06`）：
- 只填 `矛盾` 字段、不写 `#### 未决` 小节 → 报警（「有矛盾却没有可见的矛盾小节」）
- 只写小节、不填字段 → **失败**（「被标记矛盾却没有 `矛盾` 关联」）

## 5. 成本与排期（实测，用来给这一步留时间）

| 阶段 | 实测耗时 |
| --- | --- |
| 读接口 | 3 min |
| 定题 | 12 min |
| 扫结构 | 5 min |
| **采证 + 逐字核对** | **45 min** |
| 分层 | 4 min |
| 写产物 | 25 min |

**贵在裁决，不在填写。** 填不出的字段几乎不花时间；而**一条冲突单条 5–8 分钟 = 普通条目的 3–4 倍**。
→ 遇到冲突不要「先跳过去待会儿再说」，它会以利息的形式回来。

## 6. 反模式

- ❌ **按「哪个看起来更权威」选一个** —— 权威感与正确性无关，`docs/` 的错结论语气都很确定。
- ❌ **只记「有冲突」不记双方** —— 缺口清单第三类必须能让人复现你的困境（双方 + 出处）。
- ❌ **把冲突删掉** —— `已解除` 与 `已推翻` 都是资产（`COL-R08`）。
- ❌ **在子代理里裁决** —— 裁决需要回原文，且是累积判断；拆给并行子代理等于把交叉判断交出去（`COL-C05`）。
- ❌ **把 scope 差异写成真矛盾** —— 「默认关」vs「可开启」不是矛盾，是两条断言，分开写。
